## 用户流程

1. 打开菜单栏“数据与更新 → 检查更新”。启动 App 本身不自动检查或下载。
2. 点击“打开 GitHub 创建令牌”，在 GitHub 创建 fine-grained personal access token。资源所有者为 `bbbushi`，仓库仅选 `Aliciation`，Contents 设为 Read-only，其他权限不加；该账号需已有仓库读取权限。
3. 将 `github_pat_` 开头的令牌填入 Alice 更新窗口，点击“检查更新”。这与模型 API Key、Codex 的 GitHub 连接分别独立，Alice 不借用 Codex 凭据。
4. 有更新时显示版本和说明，用户点击下载。先核验签名及包内声明，成功后才出现“备份后安装并重启”。
5. 用户确认后，等待当前任务结束、停止后端写入、创建并核验数据恢复点、确认后端进程真实退出，再保存旧版应用、安装新版并重新启动。
6. 授权可在窗口内清除；关闭授权窗口不会自动注销，退出 Alice 进程后消失。重新打开 App 需重新填写。令牌失效、权限不足、附件缺失或网络中断均显示失败，不宣称“已是最新”。

0.1.1 没有联网更新功能，首次必须正常退出后手动换成 0.1.2。0.1.2 不会更新到同一个版本；后续真人双版本演练需发布更高版本。

## 授权与原生边界

- 首版使用只读 fine-grained token，不实现 OAuth 登录或长期钥匙串保存。UI 用密码输入框，操作结束清空输入值，Rust 会话只向 UI 返回 `has_token`，不返回令牌。
- 令牌仅在本次原生进程内存及请求 HeaderMap 中存在，清除授权会同时释放已检查/下载的会话；不写入配置、日志、备份、发布清单或命令行。输入必须是 `github_pat_` 格式，避免将模型 Key 发往 GitHub。
- 带授权的请求初始地址固定为 `api.github.com/repos/bbbushi/Aliciation/…`，使用 Contents 只读发布/附件 API。重定向仅限 HTTPS 443、GitHub 与 GitHub 内容主机，最多 8 次；reqwest 在跨主机重定向时移除 Authorization 等敏感头。保留系统 TLS 校验与系统代理支持。
- 更新指令只接受 bundle 内 `updates` 窗口，页面禁止导航到外部站点及创建新窗口；聊天网页不能调用该入口。创建令牌按钮仅通过固定系统命令打开固定 GitHub URL，不把令牌传给浏览器命令行。
- 不新增模型可调用能力，因此不修改 `commands.json` 或宪法；核心控制管道仍不提供任意原生更新命令。

## 发布协议与签名

采用锁定的 `tauri-plugin-updater 2.14.1`，支持标准 Minisign 更新签名，并启用 `requireSignedVersion`。开发通道为 `desktop-dev`，目标为 `darwin-aarch64`。

私有仓库的浏览器下载地址无法匿名使用。检查时先从 GitHub API 的 `desktop-dev` tag 找到已上传的 `latest.json`，再以 octet-stream 请求附件 API。清单保留标准 Tauri 字段：version、notes、pub_date、platforms。下载时按清单版本定位 `v<version>`，查找精确名称 `Alice-<version>-darwin-aarch64.app.tar.gz`，再读取其附件 API；不把令牌拼到 URL。

发布元数据限 1 MiB，通道清单声明大小限 64 KiB，归档下载限 512 MiB，展开声明总量限 2 GiB。HTTP 请求设有超时；下载与验签在安装准备前完成，失败不关闭聊天服务。签名在下载后、安装前及 updater 安装步骤分别核对。

公钥入库于 `addons/desktop/packaging/updater.pub`，同时嵌入配置。其文本去除首尾空白后 SHA256 为 `3326619cc644ffd4cb056eab128e62df0da5b3df95e7e5a5d997cbf510ae4472`。私钥仅在本机 `~/Library/Application Support/Alice Release Keys/updater.key`，目录权限 0700、文件 0600；不入库、不进 App。构建用签名工具仅在启用 `release-tools` 时生成，未打入 Alice.app。私钥是本机权限保护的未加密发布密钥，丢失后不能直接用另一把密钥为已安装客户端续更。

签名 trusted comment 包含 timestamp、文件名和目标 version。构建工具用 minisign 与 minisign-verify 双重核验生成结果。更新签名独立于 macOS 代码签名；当前 App 仍为 ad-hoc 开发签名，未做 Developer ID 与 Apple 公证。

## 兼容与安装顺序

归档仅接受 `Alice.app` 根内正常相对路径、目录、普通文件和根内符号链接；拒绝重复、越界、硬链接与特殊文件。校对签名覆盖的宿主 `Contents/Resources/release.json` 和冻结后端 `_internal/build-info.json`：同一版本和 build-id、应用标识、目标架构、开发通道、公钥摘要、维护协议与数据格式、系统下限均须一致。

本批维护协议固定 v1、读取/写入格式 v1，`migration_from` 必须为空；不接收未经实现的数据迁移。低于目标系统下限拒绝安装。

安装必须使用正式 release 构建的 macOS arm64 App。确认后复用现有 `shutdown(reason=update)`，不新增退出前模型收尾调用；收齐 `backup_complete`、正常关闭帧且真实子进程退出码成功后才进入安装。

安装前通过 ditto 将当前 App 复制到独立用户目录 `.maintenance/updates/<id>/Alice.app`，核验副本代码签名，写入不含凭据的更新记录。数据恢复点仍在 `.maintenance/backups/`。正式替换交给 updater；成功后调用新安装的后端执行维护预检及一次性 nonce 授权，通过 Tauri 正常清理并重启，将 nonce 交给新进程消费。

失败保留数据恢复点及已生成的旧程序副本，显示错误并打开恢复窗口，不自动恢复旧数据或合并对话。若新版已替换但预检失败，提示重新打开并走恢复入口。旧 App 副本是人工替换备用，不宣称有已验收的自动程序回滚。用户退出或关闭窗口等待维护结束，不在维护中强杀进程。
