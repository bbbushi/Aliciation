# 气泡输入区周期闪动：修复与人工验收

2026-11-18。用户明确现象为“发送按钮或输入区定期闪动”，不是消息重播或整窗反复出现。只读确认安装版为 0.1.19。原生 UI 工具仅确认桌面应用运行，未提交消息、捕获性能录制或完成真人复现。

## 原因

`web/desktop-chat.js` 在展开时每 1500ms 同步 `/api/chat/activity`、必要的 state 和历史。`sync()` 开始设置 syncing=true 并执行 buttons()，结束又设置 false 执行 buttons()。发送按钮 disabled 直接包含 syncing，因此即使后台和对话内容完全没有变化，也会规律变灰、恢复。CSS 的 button:disabled 设置 opacity=.45，这构成代码可确认的周期闪动路径。

输入框本身的 disabled 依赖 sending/available/enabled，没有直接依赖 syncing；用户看到输入区闪动，至少发送按钮有明确原因，不能据此声称整个输入框也被反复销毁。没有发现此路径使用 location.reload。

## 修改与并发处理

1. 常规发送按钮和发送入口移除 syncing 条件。只读 GET 不是用户提交操作，不产生忙碌视觉；实际未就绪、服务忙碌、正在发送、会话待确认、请求结果不明等原条件保留。
2. 用当前 AbortController 标识同步所有者。用户真正提交且本地条件允许时，先撤销当前同步所有权并取消旧 GET；之后仍用原 request_id/epoch/POST/SSE 流程发送。
3. 每次 GET 的 JSON 读取完成后核对所有者；等待原生通知返回后也复核。被发送操作取代的旧结果不再修改 UI、草稿、会话、来源占位或同步锁。
4. finally 只释放本次仍持有的同步状态，避免旧请求的迟到 finally 把后续同步解锁。主动让位的取消不显示同步失败；真正12秒超时或连接失败仍保留原来的失败反馈与来源隐藏规则。
5. 相同的连接文字、提示和消息 className 不重复写入 DOM。保留原节点 reconcile 和跟随/回看逻辑，不重排逐句队列，不改消息内容及呈现时长。

恢复区的“同步原请求”仍按真实核对操作设置忙碌，防止重复核对；它在没有结果不明请求时隐藏。没有把轮询改成更长间隔来掩盖问题，也没有修改主窗口或原生权限。

## 人工验收

依照项目约定，不写假模型或临时 Store，不做机器业务自测。仅静态语法、版本和包核验；安装后由真人在真实桌面资料中检查：

1. 空闲展开气泡至少观察十秒，发送按钮不随轮询变灰，草稿和输入焦点保持。
2. 在轮询发生期间点击发送/按 Enter，能正常提交一次；真实发送过程仍有忙碌反馈，完成后恢复。
3. 消息逐句揭示、末句收尾与回看/跟随保持正常；无旧消息重新播放。
4. 实际网络延迟或超时后，能继续发送或按真实状态提示核对；旧 GET 迟到不覆盖新的提交状态。只读轮询取消不导致 POST/SSE 中断或重发。
5. 服务真正忙碌/断开、会话变更、资料到期与结果不明时，原约束和正文隐藏仍有效。
