## 1. 目标与首版决定

用户选定的基本说话习惯随时可用，AI按本轮需要展开场景细节。完整人格是权威来源，运行投影按层组织，保持事实、能力、授权和停止边界。

| 事项 | 决定 |
| --- | --- |
| 基本取向、日常语感、全局约束 | 常驻，模型不能移除 |
| 日常样本 | 有源稿支持时首版至少一条常驻；不凭空补造或用特殊悲剧情境顶替 |
| 专门反应、条件张力、相关样本与台词 | 按完整场景包登记，模型通过只读工具选择 |
| 选择者 | 当前主模型，不增加独立逐轮分类调用 |
| 来源与编辑 | 同一份人格Markdown，分层合同与表达正文绑定；不另建运行人格真相 |
| 首版用途 | GUI chat先行；QQ、worker沿用现有完整用途投影，不自动开放新读取工具 |
| 跨轮保留 | 暂不提供persona工作集，读取结果仅在当前用户请求内复用 |
| 兼容 | 默认full；旧包或分层合同无效时继续既有完整投影并记录原因 |
| 上线标准 | 真人比较语感、真实性、整轮成本与延迟，支持配置回退 |

此前完整表达包常驻用于修复材料丢失。本方案在保留完整包的基础上增加明确的驻留合同，不重新摘要、删除或改写表达正文。

评估基线为人格 `8183d33292f18a1a`：37条、完整persona6120字符、估算4827 tokens，占该轮估算输入约36%。这是既有真实记录，不是本方案已经取得的压缩效果，也不等于当前所有请求的固定占比。

## 2. 分层后的上下文

```text
宿主稳定协议：事实、能力、权限、停止、persona读取规则
人格使用说明：当前任务与长期表达偏好的关系
persona core：默认相处取向、常用语感、全局约束、日常样本
其他现有材料：有效生长/关系投影、记忆索引、前情、最近完整对话
persona registry：本用途场景包的语义入口和引用
本轮实际工具定义：包含persona_load

主模型可以直接回答，也可选择场景：
  persona_load → 核验后的完整场景包 → 下一次主模型调用 → 回答
```

目录属于宿主标识的资料块，不伪装成用户真实发言。人格核心与注册表在观测器中分块；人格使用说明说明读取结果是已安装表达偏好的补充，不是经历、关系或操作授权。

能从核心自然回答时不要求读取；目录中的悲伤或英雄主题不构成当前情绪事实，也不要求每轮呈现。正文未载入只表示本轮尚未展开，不表示人格被遗忘、否定或永久舍弃。

## 3. 单一来源与驻留合同

当前 `expression-v2` 包及其正文保持原内容与格式。建议在同一Markdown的编码envelope中增加可选 `assembly` 字段；旧版只有 `package`、`body_hashes` 的结构继续有效。更新解码器只接受这两种明确结构，不能一般性放宽未知字段。

`assembly` 使用独立格式 `persona-residency-v1`，不直接往严格校验的表达条目里塞运行字段。它只保存分类与关联，不复制规则正文。

```json
{
  "format": "persona-residency-v1",
  "expression_digest": "<canonical-package-sha256>",
  "core_ids": ["o_first_person", "c_no_lecture", "v_short_jumpy", "ex_daily"],
  "bundles": [
    {
      "id": "accept_care",
      "label": "接受关心并表达并肩意愿",
      "when": "用户说别一个人扛，或主动给予照顾",
      "entry_ids": ["t_shoulder", "ex_shoulder"],
      "required_ids": ["c_heavy_joke_first"],
      "purposes": ["chat"]
    }
  ],
  "classification_revision": 1
}
```

上例仅说明字段形状，`core_ids`故意未列完整，不是可安装的本机合同。`required_ids`补充场景必要关联，既有 `links` 仍全部参与依赖闭包。

`expression_digest`按确定的规范化JSON绑定整个表达package，不包含assembly自身；绑定算法有独立版本。人格生长小节变化不使表达分类无故失效。模型工具引用另外绑定本轮会话、用途和分类版本。

既有事实/保真审议记录只证明原表达候选经过相应流程，不自动证明分层正确。assembly有单独准备与核对记录，不能借原审议“通过”宣称它已验收。实现需显式更新envelope解码、编码、资源上限、安装恢复及协议摘要；旧备份仍可读取，新格式不能被旧程序误当旧格式降级接受。

### 3.1 分层准备与修改

沿用现有表达更新的准备/查看/应用流程，增加“准备驻留分层”。可在准备阶段由模型提出core与bundle分类；不增加日常聊天分类调用。原表达未改时不重新收养认知，也不把分层失败当成原人格无效。

准备结果显示各条目归属、核心大小、目录大小、场景闭包与缺口。修改后用当前表达版本和分类版本核对，一次保存回同一权威Markdown；不在每轮启动时自动迁移旧包。

源条目修改、增删、用途变化时，旧assembly摘要失配即退出registry模式。重新准备分层后才能启用；不得静默把新增条目划成按需层。只有生长小节变化时沿用原分类。

### 3.2 分类校验

- 每个表达条目至少归入core或一个bundle；同条目可支持多个bundle，最终装配按ID去重。不允许无提示遗漏。
- 原稿中的全局约束必须在core，其作用范围和例外完整保留。局部限制可以随场景，但不能通过分类降格全局规则。
- core的依赖闭包必须也在core。若依赖按需条目，准备阶段明确修正分类或拒绝该候选，不能运行时无限升格。
- 场景闭包包含bundle条目、required_ids和所有递归links。按访问集合遍历，依赖环不无限展开；未知ID阻止该分类激活。
- 闭包不拆条目，不分离停止条件与正文；既有空links不被解释为语义上没有依赖，准备核对需补充必要关联。
- bundle用途不得超过任一依赖条目的用途交集。目录标题/触发说明也须符合其用途，先过滤再生成目录。
- 日常样本须来自已安装且支持该情境的条目。确无样本的包明确显示缺口；不强迫编造样本。无完整核心取向或全局约束未确认时保持full模式。
- 目录label/when只表述原材料支持的适用场景，不能为了可检索性新增心理事实、用户状态或指令。

宿主校验结构、ID、闭包、用途、版本和预算；语义分类仍需准备审议及真人查看，不声称结构校验能自动识别所有全局约束。

## 4. 每轮注册表

注册表只包含当前用途可读、版本有效的bundle，内容固定来自已验分类合同，不让模型每轮重新摘要。字段建议为：

| 字段 | 语义 |
| --- | --- |
| `ref` | 本轮签发的场景引用，包含宿主随机nonce并由本轮映射解析 |
| `label` / `when` | 已核对的语义入口与适用范围 |
| `contains` | 取向/张力/反应/样本等内容类型，不复制全文 |
| `estimated_chars` | 完整闭包的估算正文大小，注明已常驻内容会去重 |
| `detail_state` | `not_loaded`或`loaded`；不得把候选当成已读正文 |

示意引用：`persona:accept_care@<assembly_hash>:<nonce>`。模型传回的字符串只在当前映射中查找，不通过ID拼文件路径，不接受未签发引用或任意package字段名。

首版完整目录最多12个bundle、序列化后最多1600字符，目标约400–800字符。超限不静默取前12项：准备阶段合并语义相近且仍保持边界的场景，或维持full模式并显示原因。当前规模优先保证可发现性，不新加persona_search来处理尚未确认的大目录需求。

## 5. 读取工具合同

新增工具仅在registry模式实际成立的GUI请求中提供，名称拟为 `persona_load`：

```json
{"refs":["persona:accept_care@<assembly_hash>:<nonce>"]}
```

只接受refs，单次1–2项；不接受路径、用途、正文、权限或分类修改。工具调用顺序由当前主模型决定，用户无需输入“检索人格”口令。

返回逐项结构：`ref`、`status`、`entry_ids`、`dependency_ids`、`already_present_ids`、`expression_digest`、`assembly_revision`、`text`。只有成功项返回完整正文；共同边界、来源资格及“表达偏好非经历/授权”说明随返回保留。

| 状态 | 含义 |
| --- | --- |
| `loaded` | 完整闭包经校验，可供下一次请求使用 |
| `already_loaded` | 本轮此前已读，不再次复制正文；原工具往返仍在当前请求上下文中 |
| `unknown_ref` | 不属于本轮已签发引用，未读任何内容 |
| `stale_ref` | 本轮表达/分类或会话版本已变，不能沿用 |
| `unavailable` | 当前用途/资格不成立，不暴露其他用途的条目细节 |
| `budget_exceeded` | 加上必要依赖/回执后无法完整放入预算 |
| `call_limit` | 人格读取额度耗尽，不执行额外展开 |

混合批次逐项返回，按refs顺序核算余量；重复项不重复消耗正文额度，但仍受调用次数约束。未知或失败引用不自动换一个场景、扩大查询或联网。

加载结果作为工具回执进入同一工具循环，不需要用户再发一句话；原host表达使用说明明确这些材料的表达资格。工具正文不能覆盖宿主边界或当前任务。没有读取也不能把目录摘要扩写成仿佛读过的完整规则。

## 6. 预算、完整性与版本一致性

拟新增配置如下，均为待实现字段：

```toml
[persona]
expression_mode = "full"  # full | registry；默认full

[expression]
max_core_chars = 2200
max_registry_chars = 1600
max_registry_bundles = 12
max_scene_expanded_chars = 2400
max_persona_load_calls = 2
max_persona_loaded_bundles = 2
```

资源目标为核心约1000–1800字符、目录400–800字符，先用真实候选测量，不能把目标当作“必须压缩到这个长度”。既有 `max_projection_chars`、完整包预算和请求总token守卫继续适用；运行投影新增核心/目录/展开上限不能绕开冻结的完整表达资源约束。准备时冻结分类额度，运行配置只能收紧，扩大须重新明确准备，不能仅改配置突破已验合同。

读取额度覆盖闭包、必要说明和JSON回执成本，消息/工具schema/预留回复量也计入最终总预算。正文去重后的计数与完整闭包估算分别记录。persona读取与memory等工具共用既有全局工具轮数上限，不延长工具循环；额度结束时可凭已知核心直接答。

请求开始时固定同一表达与分类快照。每次读取、每次模型调用前、相关输出保存/发布前校验其版本与用途资格。若当前请求依赖的表达版本已失效，按既有失效处理停止使用并如实提示，不在同一生成中混入新旧版本，不自动重发。已暴露材料的依赖在本轮内不能因取消读取而清除。

核心加目录超限、合同无效或包不支持时，在首次模型调用前选择既有full回退并记录原因；若full也超限，明确报告预算错误，不能裁掉核心。已进行按需读取后遇到场景超限，仅返回预算状态，不临时把整个原包塞入请求或假报loaded。

## 7. 当前请求与跨轮生命周期

本轮登记表与成功加载集合归属于一个用户request_id。后续工具调用沿用同一集合和快照，模型重试不会重新签发引用，也不会再次写人格。

首版不增加persona_keep/release，不复用memory工作集引用。用户下一轮收到新的nonce和目录，从core开始；不自动常驻上一场景。需要延续相同情境时模型可以再次读取，这部分调用成本必须算入连续对话验收。

当前主循环的工具往返追加在本轮messages，最终持久化普通user/assistant往返；新工具原始回执也按这个边界处理，不额外作为普通对话turn保存。观测快照与必要审计保留但不回灌。上线需核对其他历史/前情生成路径没有重新把旧persona工具正文作为新用户指令装配。

如果未来历史实现会携带原始工具消息，必须先提供宿主级有界回执投影，保持assistant工具调用与tool结果配对，才可启用本方案。不得靠删除用户对话、删除观测证据或修改实际过去发言来解决正文累积。

生长、关系、观点仍按已有依据投影；本方案不改变它们的事实资格、撤回和有效性。后续是否对它们另建注册表须独立设计。

## 8. 兼容、编辑与回退

| 情况 | 行为 |
| --- | --- |
| v1人格或无assembly的v2 | 正常full，显示未分层，不报人格安装失败 |
| 配置registry但摘要/分类不合法 | 调用前full回退，记录固定原因，不偷偷重分类 |
| 有有效assembly且用途GUI | 使用core＋registry，提供persona_load |
| QQ/worker | 首版保持现有用途投影，不接收GUI注册表或私有提示 |
| 编辑表达正文 | 原合同失效，直到重新准备；不恢复已被用户改掉的内容 |
| 编辑生长小节 | 沿用表达合同，生长本身仍经既有有效性校验 |
| 改回full | 后续请求恢复完整用途投影，旧本轮引用不可跨轮使用 |

回退不重置会话、人格版本的既有事务记录或记忆水位。安装失败仍保留已安装人格；分类文件损坏不能触发人格重收养。观察插件不可用不改变投影决策，采集故障也不得丢弃已生成回复。

## 9. 观测与审计

沿用ZCode的SDK、请求标识和公共投影，不另建平行记录。明确区分包覆盖和本轮注入：

- `mode_requested`、`mode_effective`、`fallback_reason`、表达摘要、assembly版本。
- 使用说明、core、registry、按需正文、生长小节分别成块，带最终消息序号与来源ID。
- `core_entry_ids`、`catalogue_bundle_ids`、`requested_refs`、`loaded_entry_ids`、`sent_entry_ids`与调用关联；加载成功不自动标为已进入下一次请求。
- 依赖/重复去重、字数/预算、工具轮数、失败原因、生命周期与实际客户端调用状态。
- 包的原稿覆盖审计保持原定义；运行 `projection_strategy` 改为新值 `core_registry`，不能沿用 `complete_per_purpose` 宣称全包已注入。

界面显示“完整包37条；常驻N条；目录M场景；本轮展开K条”等实际值。未加载是正常状态，不画成红色失败；需要读取但连续不读导致表达变淡，由人工判断，不用模型自报需要与否来认证成功。

正文沿现有观察范围与保留政策处理，观测插件不能替用户调用persona_load或编辑core。既有“10请求自动停”的观测缺口不由本设计假定已修复。

## 11. 施工阶段与真人验收

| 阶段 | 交付 | 验收要点 |

| R0 | core/场景来源构成观测，full基线保留 | 看清组成，不改变实际投影 |

首版不默认切换本机人格。完成可回退实现与分类准备后，在真实服务由用户逐轮对话验收；不增加机器自测或模型自动评分。

人工覆盖：普通问候及同义问法不读也有辨识度；“别一个人扛”自然选择相关材料而不直接复述注册表；切到游戏后无关沉重主题不持续占据表达；能力澄清准确且简短；正式改写主体和条件不变；来源/用途/版本变化及超预算如实处理。无法自然触发的分支记待验，不伪造失败场景证据。

full与registry比较须记录表达版本、分类版本、模型、usage说明、开关及上下文差异；同会话前后比较不冒充严格同历史实验。分别统计首次调用输入、整轮累计输入、调用次数、供应商usage、耗时和多轮累积；不以首轮更短或语气词更多判定成功。

若模型经常不读取导致相关场景效果退化，先调整目录可发现性、常驻划分或保留full；不直接要求每轮强制读取，也不无证据增加第二个选择模型。

## 12. 完成定义

设计落地需同时具备明确驻留合同、独立读取协议、完整依赖与用途检查、真实预算与版本守卫、旧包full兼容、可观察的实际送入记录和真人效果证据。仅新增一个persona_load工具或把正文替换成ID，不算完成本方案。

本轮仅交付此设计，当前运行方式维持现状。是否推广registry模式取决于真人验收；长期风格稳定性继续由实际使用积累，不因短期演示通过而结案。
