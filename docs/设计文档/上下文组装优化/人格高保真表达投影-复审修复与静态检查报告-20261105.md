## 1. 本轮决策与边界

N1 保留旧格式默认保护，增加逐节明确选择；不以取消保护、删除缺口或重做认知导入取得“可应用”。N2 对自动整条替换采取保守的一对一身份条件，拆并不明确时停止本次合入。N3 将新增再删除记作有效用户撤销历史，允许净正文修改归零，不把用户编辑状态伪装为重新通过模型审议。

本轮修改六份源码：`alice/expression.py`、`alice/expression_prepare.py`、`alice/expression_update.py`、`alice/service.py`、`alice/retrieval.py`、`web/app.js`。新增两份本轮文档，并更新 AGENTS“当前”。核心仍只用标准库，GUI 仍为原生 JS；同一人格 Markdown 是运行权威，私有审计 JSON 不成为运行兜底。宪法存在事实已同步旧格式范围选择与拆并限制。

R2/R3/R5/R6/R7/R8 原静态防护继续保留；本轮没有把这些旧结论改写为真人通过。P1b 默认关闭。人格表达更新仍只写表达三节、人格版本和操作标记，不改认知、生长内容、会话或维护水位。

## 2. N1：明确范围后重新准备、双审和应用

### 2.1 三种逐节策略

| 选择 | 最终候选的处理 | 资格与未解决问题 |
| --- | --- | --- |
| `preserve`／保留当前，默认 | 当前该节全文作为原有保护范围；新源该节条目不会静默覆盖它 | 未合入的源必需项和必需场景继续形成缺口，不把保留推定为删除授权 |
| `replace`／采用原稿 | 用户明确授权本次用新源完整条目替换当前该节 | 新源条目仍须结构、事实、保真、用途与预算核对；不保留未选择的旧正文 |
| `merge`／保留两者 | 保留新源该节条目，再将当前全文追加成一个 GUI 私有用户配置条目 | 作为 `add` 记录，不是整节覆盖；不猜测去重、不冒称化解冲突，后续改源仍保留该用户新增 |

同一必要规则的 v1 不再只有默认保护后被阻止这一条路径：用户可在正常表达入口选择采用原稿，重新准备最终候选，通过既有门槛后显式应用。原稿新增必要项时，可选择保留两者使新源与当前配置都进入核对。默认不替用户作此选择；含冲突的合并仍可能不就绪。

跨节依赖因某节保留而失效时，仍走已有依赖闭包处理，不能通过取消必要标记或场景来凑成功。旧全文追加始终是 `user_config`、私有、仅 `chat`，不继承源条目的 QQ/worker 资格。

### 2.2 版本绑定与审议顺序

1. `ChatService.persona_expression_update` 的 `prepare` 载荷增加 `legacy_choices` 和可选 `source_hash`。选择只允许三个表达标题及规定值；缺省逐节补为 `preserve`。当前已是 v2 时拒绝旧格式选择，不能借它覆盖已有逐项修订。
2. 准备先核对人格 revision/session epoch；所选审计源携带摘要时逐字校验读出的原稿。计划冻结当前版本、当前正文、原稿摘要、逐节选择和当前→候选差异。准备协议升至 3；旧未应用候选需重新准备，查看和应用两处都设门槛。
3. 选择在最终包构造阶段执行，发生在双审之前。私有 `legacy_resolution.json` 记录当前正文与选择。保真核对同时看到这份范围证据、原稿及最终包；初次核对与一次样本补位后的复核都使用相同范围。事实核对仍只看完整成品及用途，不收到来源、适配理由或上一份判定。
4. GUI 展示每节选择、当前→候选与原稿→候选差异；修改准备输入后要重新准备。历史候选显示冻结选择；调整范围从该记录回到准备入口，重新取得当前人格绑定并产生新候选。
5. 应用仍只接受候选 token、revision、epoch，不接收新范围。服务器核对协议、冻结版本、原稿/候选 hash、预算及最终包审议后提交，不在应用时重新拼接未审正文。

没有放宽现有 GUI 来源/意图、服务锁或用途权限；模型没有替用户选择、激活或回退的工具。传输重试仍属于单阶段既有调用机制，界面不自动重跑完整准备链。

## 3. N2：条目身份不再由唯一源集合代替

整条用户修订合入前，宿主需要证明旧条目与新条目是一对一。核对范围包含与被修改项同组且共享源的全部旧基线，不只检查有用户改动的条目；未修改的 V2 也参与判断，因此旧 V1/V2 合成新 N 不能只因 N 是唯一同源候选就被 V1 覆盖。

`_match_base(new, base, baselines)` 先扩展同组且源集合相交的旧基线连通范围，再取新包与该源范围相交的条目；两边数量必须相同。每个旧项都须按完整源集合和正文/范围摘要唯一对应一个新项，各旧项不得共用新项。全部编辑先对不可变 `candidate_baseline` 校验，再写入替换；删除项及未修改关联目标也遵守此条件。

旧新 ID 变化本身不直接构成错误，也不充当身份保证。同原稿版本下，仅在源集合与完整内容已经相等但出现重复候选时，允许以相同 ID 消歧；不同版本不使用这个退路。跨原稿版本使用完整源单元指纹，旧新对应源指纹都须唯一，缺少定位或重复时停止。正文改写、拆分、合并或内容重复造成身份不明确时，不猜语义、不删无关项。

这是保守的自动合入边界，未实现合并条目内部的片段级修订，也不承诺任何模型改写后均可迁移。此类拒绝保留当前人格，人工记录应区分“歧义正确被阻止”和“一对一自动合入成功”。

## 4. N3：净修改归零保留有效撤销证据

原来的 `add` 在删除时直接消失，造成 `edits/sections` 为空却保留 `user_config/invalidated_by_user` 审议状态。现在删除已记录的用户新增时，移除该 `add` 并在 `cancelled_additions` 保留被撤条目 ID、完整条目摘要与上一版审议摘要；当前 `review_digest` 同时绑定这些记录。

撤销记录经过严格字段、摘要、唯一性和容量校验，被撤 ID 不得仍存在于成品或当前修订条目。内嵌记录只保留本次实际保存的撤销证据；历史保存留在原人格修订审计，不随日常编辑无界增长。重用同 ID 会清掉旧撤销记录；已消失且没有源身份的新增基线也会清理。净正文修改归零仍是有效用户配置状态，不恢复模型“双审通过”，也不会恢复曾失效的来源、QQ 或 worker 资格。

普通空账目不因此放行。解码依然要求同版摘要和有效修订证据；只有 `edits`、整节范围或合法新增撤销记录才能支撑用户配置状态。重新从原稿准备时，没有净表达变更的撤销历史不当作源删除授权，最终候选仍重新双审。
