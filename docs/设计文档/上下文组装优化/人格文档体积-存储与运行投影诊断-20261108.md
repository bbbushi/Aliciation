## 文件为什么特别大

`expression.encode_sections` 为了保持“单份 Markdown 权威、正文和结构化资料同版”，把 package 与正文哈希封装为 JSON，UTF-8 编码后再 Base64，嵌入首个表达小节的 HTML 注释。可见表达正文又以可编辑 Markdown 保存一遍。它是存储表示选择，不是模型把人格自述写到了五万字。

本份注释的解码 JSON 为27611字符、36612字节；Base64正文48816字符，加注释标记后48845字符。Base64相对字节流约增加1/3；中文UTF-8占多个字节，所以不能只按“JSON字符数乘1.33”推算。

JSON既包含27条完整表达及条目级id/scope/来源/依赖/用途/审查等字段，也包含来源单元指纹、去向与覆盖核对。按紧凑JSON的值长度举例：

- 六组表达条目数组合计11787字符；其中实际内容字段2237字符、范围字段1126字符，其余大量是条目字段、标识、来源与依赖等结构。
- source_units：6404字符、20个来源单元，内容是行号、类型及heading/columns/raw哈希，不是又保存了一整份原稿正文。
- destinations：3489字符；coverage：1809；coverage_contract：1745；coverage_report：452。

这些是各字段值的独立长度，未计其键名和外层分隔符，不能直接当作完整JSON的精确可加分解。

## 聊天投影为什么也比原稿长

运行时 `persona_context.render_full` 不把元数据注释整块送给模型：先解包，再用 `expression.project` 生成用途投影，替换底色三节。故五万多字符的存储文件不等于每轮五万多字符输入。

但本次完整运行人格5449字符，相对1840字符原稿仍约2.96倍。确实存在第二层膨胀：

1. 原稿中的一句反应，被展开为范围、触发、第一/后续反应、停止条件等多个字段。
2. `scope` 常再次复述正文已有的主旨、触发和例外。比如 r_praise 的 scope 已写“被夸先得意，再自嘲降温”及场景，trigger/first/then 又重复相同结构。
3. 条目带id、类型分组、字段标签和依赖表示；规则或张力反复说明共同边界。
4. 运行时另外添加457字符表达使用说明，以及来历/空生长小节等。这个开销不会因按需目录自动消失。

转换还包括角色经历/身份向AI可使用表达偏好的适配，原稿与投影内容并非逐句等价，因此不能把所有差额都叫“无用字数”。但没有必要为保真而在每项里重复相同条件或公共边界。冗长条件可能稀释可执行语感的相对显著性，这是需要真人对照验证的推断，不能仅凭尺寸断言语气变淡的唯一原因。

## 优化方向（本轮未施工）

- 分开设计“可靠存储表示”和“模型阅读表示”。存储的来源、审计、版本约束保留；模型只拿到本轮需要的表达内容和必要条件。
- 若更换存储格式，应把正文/结构包/审计做成有摘要绑定、版本和原子发布的可移植单元。不能直接把注释移到不受版本保护的独立JSON文件，破坏现有同版校验和回退兼容。
- 聊天投影优先消除 scope/trigger/正文的重复和通用字段标签，公共约束统一表达，保留条件例外、场景闭包及说话样本，不以概括性格口号替代样本。
- 分层按需减少当轮送入的场景正文；目录压缩解决registry_too_large；二者都不会自动缩小落盘元数据。文件瘦身也不会自动改善语气或节约已经排除的注释token。
- 页面应分别展示存储文件大小、可见正文大小、实际当轮投影大小，避免把存储膨胀与上下文膨胀混为一谈。
