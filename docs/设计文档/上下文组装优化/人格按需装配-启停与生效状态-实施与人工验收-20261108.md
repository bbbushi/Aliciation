# 人格按需装配：启停与生效状态

日期：2026-11-08。承接《人格按需装配未启用-本轮观测-20261108.md》。本文记录代码补齐和待真人验收范围，不把静态检查或服务启动当成聊天效果验收。

## 解决的问题

之前“应用分层”只保存人格里的 assembly，配置仍是 full。页面没有切换入口，导致已经安装人格甚至保存分层，也可能继续完整投影。09:00:45 的真实请求属于未分层且未启用，不是模型忽略了按需目录。

现在的入口是“人格 → 人格装配”，从原稿更新表达页面也保留同一管理面板。流程为：

1. 准备分层：显式点击后调用已配置模型，生成暂存候选；当前分层和装配模式不变。
2. 核对并保存：查看核心原文、每个条目的归属与原文、场景及依赖闭包；保存仅写分层，不暗中切换模式。
3. 启用按需装配：有效分层通过检查后才可点击。保存配置并同步发布给当前服务，下一条本机网页请求生效，无需重启。
4. 恢复完整装配：下一请求恢复完整用途投影，保留已保存分层，方便切回比较。

准备分层会调用模型；状态查询、启停和刷新不调用模型。此次施工没有自动为本机人格执行分类或切换模式。以后新导入、回退或编辑可能使分层缺失/失效，宿主保留原有回退行为，不静默重新分类。

## 状态的含义

页面分别显示“分层保存”“配置保存”“当前服务选择”“下一条本机网页对话预计”。

| 情况 | 页面应说明 |
| --- | --- |
| 没有分层 | 尚未保存有效分层，说明先准备、核对、保存 |
| 分层有效但 full | 已保存且通过校验，尚未启用按需，下一轮仍完整 |
| 分层有效且 registry | 按需已启用，下一轮预计按需 |
| registry 但分层无效 | 当前服务选择按需，但下一轮回退完整，显示原因/校验问题 |
| 配置文件外部改动 | 不再声称配置与服务一致，禁止界面覆盖；按提示重启加载外部配置或人工处理 |

页面预期不是“模型已经收到”的证据。页面与聊天共用 `persona_residency.activation_status`，资格检查覆盖渠道、人格包、分层、深层校验及聊天目录。真正发出的每轮材料以观测器的请求/调用为准，面板提供观测器链接。新设置不重写旧请求记录。

registry 当前只用于本机网页主对话。QQ 及协作用途保持原有投影。没有 persona_load 调用未必失败：普通问题可直接靠常驻核心回答；需要分别核对工具是否提供、场景是否选择、正文是否进入下一次模型调用。

## 配置与并发边界

公共管理入口仍为 `ChatService.persona_residency` / 本机 GUI 专用 `POST /api/persona/residency`。新增 `set_mode`，字段必须恰为：

```json
{
  "action": "set_mode",
  "mode": "registry",
  "config_revision": "状态返回的配置版本",
  "session_epoch": "状态返回的会话身份",
  "persona_revision": "状态返回的人格版本",
  "expression_digest": "状态返回的表达摘要，旧格式可为 null",
  "classification_digest": "状态返回的分层摘要，无分层为 null"
}
```

`mode` 只允许 full/registry。请求沿用渠道管理占用、worker 控制锁和服务锁，不跨已接受的对话切换。在写盘前核对会话、人格、表达、分层和配置版本，registry 还必须满足当前可激活条件。旧页面、另一标签页或外部编辑导致的冲突拒绝保存；配置冲突返回 409。

配置编辑复用既有模型配置写入原语，扩展为普通表的单行字符串键更新：只改 `[persona].expression_mode`，保留其他字段、注释和密钥；对整份 TOML 解析结果检查仅预期字段改变，复杂写法无法可靠保留时拒绝。临时文件权限 0600，fsync 后核对版本并原子替换；文件成功后同锁更新内存及服务配置版本。服务未绑定配置文件时只读，不意外写到本机默认配置。

页面对本面板的写操作禁用重复点击，刷新结果有序发布，返回旧页面的异步请求不覆盖新页面。原分层页面缺少局部 DOM 构造函数的问题同时修复。

存在事实清单已补充这一管理能力，并明确 AI 不能自行保存分层、切换模式或把未读目录当已读正文。
