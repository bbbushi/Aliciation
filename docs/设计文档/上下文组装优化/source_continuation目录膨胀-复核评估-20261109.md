# source_continuation目录膨胀：复核评估

2026-11-09。按用户提供的ZCode分析，核对现有渲染代码与真实观测快照。结论：**重复目录值得优先优化，但1500字符目标与“整份策略相同”没有得到本快照支持；目录压缩也不等于C01依赖传播已经解决。**

本轮只读观测元数据/正文快照与相关历史正文长度，做内存中的尺寸分析；不改源目录渲染、活库、配置、权限或运行服务，不调用模型。

## 2. 重复具体在哪

### 历史消息→来源集合

- #33–#38共6条消息绑定同一组4个来源。
- #39–#46共8条消息绑定同一组7个来源。

逐条重复32字符packet ID确实浪费。按相同来源集合分组、每组保留准确turn_ids，可以无损表达宿主原映射。不能把14条全部写成同一组7来源，也不能用包含空隙或不同来源集合的范围代替实际消息集合。

### reading_policy

7包的policy JSON值合计1695字符。5份贴吧策略每份317字符，但**5份内容各不相同**；另外2份55字符策略相同。

贴吧共同字段有：reader版本、请求回帖/楼中楼的开关、楼中楼实际数量与部分标记、发帖时间依据、停止原因、文本限额。共同部分规范化JSON约241字符。

不同字段必须逐来源保留：

| 字段 | 5个来源的实际值 |
| --- | --- |
| tieba_pages_read | 1 / 4 / 3 / 2 / 2 |
| tieba_reply_count | 20 / 88 / 70 / 35 / 36 |
| tieba_published_at | 每个来源不同 |

因此建议“公共基底 + 每包差异”，不能因同一个reader版本就把整份policy归并。coverage、抓取/过期时间、URL也仍按来源保留。

## 3. 体积目标的修正

7029减2700再减1400为2929，并不是1500。只有所述两项措施，不能直接推出1500目标。

本轮对同一真实快照做展示结构的内存尺寸估算：

- 每来源保留完整packet_id、标题、URL、两个时间和coverage。
- 来源表增加短展示编号；消息按来源集合分组，记录准确turn_ids。
- 贴吧policy提取共同字段，每来源保留差异；其他policy保持。
- 保留原198字符前导。

得到约**3213字符**，较7029减少约54%。这只是候选序列化尺寸，未接入应用，也未认证模型理解、实际token节省或工具兼容；渲染说明和结构调整还会改变最终大小。

进一步精简到1500需要额外取舍或更紧凑编码，必须逐项证明可还原的信息与出处映射，不能以删除独有coverage/时间/阅读范围换取“零损失”口径。

## 4. 对C01的解释

本证据证明C01有明显的**表示成本**：共同来源集合随着每条消息重复出现。近期快照6819→7029也说明消息数量变化能继续增加目录。

复杂度更准确地描述为消息→来源边数E，加每来源元数据开销，最坏E约为消息数×来源数。窗口长度、来源额度和上下文预算有上界；不宜说会无限增长。即便达到上界，每轮仍可能反复承担较高固定成本。

“直到移出近期窗口”不能当作自然结束保证：当前实现会把已恢复历史的来源绑定到新轮，新轮又进入近期窗口。旧轮退出窗口，不等于其来源集合已经没有后继。

目录去重只改变展示，不解除来源依赖、不恢复普通记忆准入。C01的结束条件需要另行设计实际停止暴露来源衍生材料的边界；不能直接按话题变了或模型说无关而解绑。

## 5. 建议的施工边界

优先做只影响渲染的目录规范化：

1. 每包元数据保留一次；短编号仅用于本块展示，完整packet_id至少在来源表保留一次。
2. 相同来源集合定义一次，映射准确历史消息集合；分组不改变其宿主真实依赖。
3. 策略先规范化比较，相同值可共用；部分相同使用共同基底+差异。不得遗漏差异或借默认值改变含义。
4. 压缩格式不新增工具授权。模型调用若要求真实packet ID，继续使用真实ID；短编号不能冒充现有工具引用。
5. 预留预算与实际发送共用同一渲染器，观测记录新格式版本、真实字符/token估算、来源数、消息数和映射组数；不再同时发送旧目录。
6. 来源失效、渠道资格、依赖绑定及提交/发送前复核保持原路径。编码压缩不能绕过这些保护。

真人验收同时检查：出处能正确对应、不同帖子阅读范围不串、ID工具调用不误用、来源到期仍失效、实际SDK不重复新旧目录。数据字段可无损还原不自动代表模型理解效果相同。

本次建议认可优化方向，纠正测算与策略合并前提；尚未授权或实施新的渲染改造，先前多批compact修复保持。
