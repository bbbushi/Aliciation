# 人格分层准备：目录超限诊断

2026-11-08。用户实际操作后反馈：“分类未通过结构校验：registry_too_large。当前分层与模式保持不变，可重新准备。”

## 已确认的原因

失败发生在准备分层后的宿主预算检查：渲染后的聊天场景目录长度超过 `max_registry_chars`。当前本机该上限为默认 1600 字符；这是目录字符数，不是 token 数，也不是完整人格或核心正文的大小。`alice/persona_residency.py` 的 `validate_contract` 以 `len(catalogue_block(...))` 检查，并返回 `detail: {chars, max}`。

实际目录包括 84 字符说明、外层 JSON、每项场景的本轮引用（含分层摘要和 nonce）、label、when、contains、estimated_chars 和 detail_state。因此即使场景标题很短，完整目录仍可能超预算。场景数量上限 12 是独立上限，不保证 12 个场景一定能装进 1600 字符。

本机当前仍是 fingerprint `31c6596013afdbfa` 的人格，27 条表达项、3 条样本（样本包含在27条中），没有已安装 assembly，配置为 full。本次未通过的结果没有应用，不能据此判断主对话的按需读取效果。

## 无法从现有记录确认的部分

分类失败时 `prepare_classification` 丢弃候选，仅把问题列表返回页面；`residency_prepare` 不持久保存失败详情。本次调用未带 llm observation 参数，也没有相应新调用回执。服务日志没有失败正文。网页只取 `issues[].code`，丢掉了已经返回的 chars/max。浏览器状态读取超时，用户贴出的实际错误文字是本次失败的直接证据。

故无法还原这次到底生成了多少个场景、目录实际多少字符，或具体哪个标签/适用说明占用过多。不能把“场景拆太多”“某个条件写太长”当成本次已经证实的事实。

## 施工缺口与建议

1. 页面展示“实际目录 X / 上限 1600 字符”等可读明细，同时保留原错误码。
2. 失败也记录绑定表达版本的分类候选、实际预算明细和失败原因，并接入调用观察；失败记录独立于可应用候选，不能被误安装。读取历史失败不发模型请求、不自动重跑。
3. 分类准备时提供宿主实际渲染格式及开销说明；可以设计一次受控、明确预算的分类修订，凭具体超限数缩短目录说明或合并合适场景，再完整复核用途、覆盖和依赖。只改分组与目录元数据，不删改条目正文，也不把本应按需的条目全塞核心来绕过检查。
4. 先改善分类与可观测性，不仅为了通过而放大目录额度。若在合理分类后仍需增加额度，再结合真实上下文总预算与收益评估。

这些是后续优化建议，本轮仅诊断，未修改运行代码/本机配置/人格，没有重新分类、模型调用、机器测试或重启。上一轮的启停流程已部署，当前服务仍为 PID 9832。
