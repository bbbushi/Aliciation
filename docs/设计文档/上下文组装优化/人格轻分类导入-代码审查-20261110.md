## 3. 逐项证据与修复要求

### R01 — 将候选安装计划纳入归档恢复事务

定位：[service.py:880](/Volumes/workspace/Aliciation/alice/service.py:880)、[persona_material_prepare.py:390](/Volumes/workspace/Aliciation/alice/persona_material_prepare.py:390)。

新 apply 先生成只在内存里的 candidate_md/op_id，随后调用 _archive_locked()，没有传 plan。旧会话和整个 persona 目录（包括暂存候选）被搬走；_archive_locked 的 plan=None 分支会直接把 reset 日志标为 completed，然后才调用 material_commit。

触发：进程在归档完成、新 install 写入候选前退出，或 install 最初写盘失败。旧数据仍在归档，不能说永久删除，但当前活动库已空，重置日志没有候选计划且已完成；启动恢复不知道这是一次未完成的人格安装，暂存候选也不在活动目录。原有安装日志只能保护归档后新库内部的提交，无法补上这个窗口。

修复：在归档前持久化经过验证的完整安装计划，将它纳入 persona_reset 的计划校验、摘要、epoch 和恢复路径；直到安装确认提交后再 complete。重放同一操作返回同一结果，不生成新 op_id 或重复归档。不能通过手动把旧候选复制回来代替事务修复。

### R02 — 排空协作必须在 Store 锁之外

定位：[service.py:863](/Volumes/workspace/Aliciation/alice/service.py:863)、[service.py:878](/Volumes/workspace/Aliciation/alice/service.py:878)。对照 [worker_runtime.py:1192](/Volumes/workspace/Aliciation/alice/worker_runtime.py:1192) 和 [worker_reports.py:86](/Volumes/workspace/Aliciation/alice/worker_reports.py:86)。

material_import 在包含 self._lock 的 with 内 drain 和 join。drain 明确要求不持 Store 锁，退出的协作线程需要同一锁落账；join_worker_reports 的 finally 也需要该锁。RLock 只允许同一线程重入，不能让被 join 的线程取得锁。

触发：存在正在运行或收尾的 worker；drain 的 join 超时可报 worker_draining，报告线程的无期限 join 还可能形成永久等待。无活跃 worker 的假回执用例不能覆盖这个问题。

修复：参照既有 install_persona，保留控制槽和 worker 控制锁，释放 Store 锁后 drain/join，再拿锁完整复核候选、epoch 和渠道，最后归档提交。

### R03 — 新格式必须接入实际模式控制入口

定位：[expression_update.py:753](/Volumes/workspace/Aliciation/alice/expression_update.py:753)、[service.py:832](/Volumes/workspace/Aliciation/alice/service.py:832)。

触发：默认 full 配置下安装原文材料，再通过“人格装配”启用按需，无法正常启用；若配置本来为 registry，运行可能启用而页面仍报告不就绪。

### R04 — 共同上下文不能绕过待确认/暂停/存档状态

定位：[persona_material.py:344](/Volumes/workspace/Aliciation/alice/persona_material.py:344)、[persona_material.py:420](/Volumes/workspace/Aliciation/alice/persona_material.py:420)、[persona_material.py:500](/Volumes/workspace/Aliciation/alice/persona_material.py:500)。

bundle_closure 只阻止 isolated/paused，不要求依赖已接受，也不拒绝仅存档。core_text 和 project_full 直接把 context_ids 加入正文，完全不检查这些依赖的分类状态。validate_material 也不检查核心引用是否为已接受表达材料。

触发：已接受表达块依赖某个待确认或仅存档块；直接选择前者即可把后者带入。即使一个依赖被标 paused，full 与 core 也仍会发送它。闭包仅展开一层，后续人工关系产生多层依赖时还可能遗漏必要条件。

修复：建立一个供核心、full、场景、预览和安装共用的闭包函数，检查每个成员的用途和状态。上下文尚未确认时让整个相关材料单元待确认，不能偷偷提升资格；表头等结构上下文如需特殊资格，应由宿主显式标注并验证，不能把所有 context 都视为可读。保证递归闭包、顺序及去重一致。

### R05 — 坏行必须隔离，不能靠未捕获异常退出

定位：[persona_material.py:387](/Volumes/workspace/Aliciation/alice/persona_material.py:387)、[persona_material.py:399](/Volumes/workspace/Aliciation/alice/persona_material.py:399)。

修复：先检查字段集合、必需字段、每个 ID 的字符串类型，再做 membership；允许默认值时使用显式规范化后的行。把坏行定位为 isolated，不捕获后假装已接受，也不将重复冲突任意取一条。不能把这些问题统称为模型不稳定而要求用户重跑。

### R07 — 按列表项分块，提供超长块的实际处理路径

### R08 — 同一份冻结合同计算安装、预览及实际发送预算

定位：[persona_material_prepare.py:380](/Volumes/workspace/Aliciation/alice/persona_material_prepare.py:380)、[persona_material.py:321](/Volumes/workspace/Aliciation/alice/persona_material.py:321)、[context_persona.py:229](/Volumes/workspace/Aliciation/alice/context_persona.py:229)。

存在数个相关断点：

- 分类接受 bundle 后未隔离 bundle_too_large 等局部问题；安装把所有 bundle_ 问题作为整包阻断。一个无关场景超限，仍会拖垮完整导入。
- 预览 installable 仅看核心是否非空及长度，未核对核心分类、完整 scene 回执、目录、full 或实际请求模式。
- 安装只尝试 full 投影，没有检查新 registry 实际目录。目录超 1600 时到聊天构造 MaterialRegistryContext 才抛异常，loop 没有捕获并执行承诺的 full 回退。
- 原文 full 超限但 registry 完整可用的候选也被一律拒绝，缺少设计要求的“支持哪些模式”区分。
- material 的合法字段不包含 limits，准备的 cap 只在外层 record；effective_limits 永远取不到材料冻结额度，回到默认值。较紧配置准备后放宽配置，会扩大原候选的实际额度。
- MaterialRegistryContext 不检查实际 core_chars 和 core＋目录＋已载入正文的 max_projection_chars；与旧后端 fits 合同不同。pending_blocks 初始为空，还会重复返回已经常驻的块，既浪费回执额度也与去重声明不符。

修复：候选必须含可验证的冻结额度，按真实 renderer 计算 core/目录/回执/全用途预算和闭包；局部超限隔离到具体场景，显示剩余支持模式。安装、状态、模式切换和每轮运行复用同一判断。初始已提供集合应包含核心闭包，不能靠一次全局 token 守卫代替人格专用预算。

### R10 — 补齐新格式的人格查看、演化和恢复消费者

定位：[service.py:218](/Volumes/workspace/Aliciation/alice/service.py:218)、[persona_context.py:346](/Volumes/workspace/Aliciation/alice/persona_context.py:346)、[persona.py:1063](/Volumes/workspace/Aliciation/alice/persona.py:1063)。

persona_view 仍直接调用旧 expression.decode_sections，合法新封套会进入 format=invalid，显示“表达元数据损坏或未知”。这不是仅仅暂不支持旧编辑器，而是把正常新格式误报损坏。

validate_expression 仍要求 chat/qq/worker_summary 全通过，而材料格式明确拒绝后两项。普通有据生长在付费取得提案后，_commit_section_changes 调用此函数必然失败；下载新格式 Markdown 后从既有直装路径重导，也会在安装前被拒。不能认为新主聊天分支接通就代表所有已存在消费者兼容。

修复：各消费入口按格式分派，展示原文版的完整可读材料；校验已声明支持的用途，对不支持用途在入口明确拒绝。有据生长应只变生长小节并保留材料封套；恢复下载的新格式时走正确的用途及事务门槛，不要求其伪装成旧包。

### R11 — 应用必须绑定用户看过的候选修订

定位：[persona_material_prepare.py:359](/Volumes/workspace/Aliciation/alice/persona_material_prepare.py:359)、[persona_material_prepare.py:412](/Volumes/workspace/Aliciation/alice/persona_material_prepare.py:412)、[web/app.js:1265](/Volumes/workspace/Aliciation/web/app.js:1265)。
