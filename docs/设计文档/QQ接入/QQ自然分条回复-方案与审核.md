# QQ 自然分条回复：精简审核版

2026-10-30 · **用户已批准范围并授权开工；实现与验收状态见[实施记录](QQ自然分条回复-实施与人工验收.md)**

**建议先只改 QQ 的消息组织和发送：把一轮完整回复，按自然段和意思相近的句群，发成 1～3 条真实消息。** 不增加模型调用，不改变人格、记忆或网页的完整回复。

## 1. 希望看到的效果

原来一条消息：

> 今天安排得挺满，今晚可以慢一点。
>
> 那件小事明天处理也来得及。
>
> 你现在想聊会儿，还是先安静待着？

改后依次发送三个气泡：

1. 今天安排得挺满，今晚可以慢一点。
2. 那件小事明天处理也来得及。
3. 你现在想聊会儿，还是先安静待着？

而“在呀。刚把手头的事放下。”仍是一条，不按每个句号拆开。以上均为合成示例。

## 2. 分条规则

- **自然段优先。** 一段承接、一段解释、一个追问，可以各自成条。
- **避免碎片。** “嗯”“好呀”这类极短承接并入相邻内容；短回复通常只发一条。
- **长段才考虑句群。** 尽量在完整句子结束处拆；不拆坏引号、链接、数字、列表、代码或 emoji。没有可靠边界就少拆。
- **最多3条。** 超过时先合并相邻内容；仍放不下，就明确提示“后文未发送，完整回复请在本机网页查看”，不静默丢内容。
- **固定最小1秒间隔。** 不随机模拟打字；新追问先排队，上一轮发完或停止后再处理。

## 3. 怎么做、改多大

推荐在 **QQ 桥里增加本地切分规则**，复用已有发送循环。当前桥只在文字过长时切分，所以多段短文字仍会挤在一条里；只改提示词不能解决实际发送问题。

| 要改 | 保持原样 |
|---|---|
| QQ分条规则、发送记录及恢复处理 | 核心仍生成并保存一份完整回复 |
| 桥账本升级，固定每条内容和顺序 | 一轮仍只写一对用户／助手记录，拆条不增加记忆提取、工具调用或P1核查 |
| 网页QQ状态文字，说明可能部分发送 | 网页继续显示完整回复，不跟着拆气泡 |

**不需要改变核心公共接口或会话架构，也不新增依赖。** 需要升级桥自己的投递账本，这部分用于防止重启后重新切分造成重复或遗漏。

另一种做法是让模型输出“消息数组”。它可能更懂表达意图，但要改变生成契约并处理格式失败；建议先不做，等人工体验证明本地规则不够自然，再单独评审。

## 4. 失败时怎么处理

发送前固定整轮分条内容；配置变化或重启后，旧回复也不重新切。

- 已成功的条目不重发。
- 明确限流可以有限退避重试；发送结果未知时停止本轮自动发送，先由本人到QQ核对。
- 后面没发出的内容仍保留在网页；不会为了补发而重新调用模型。
- 已发出的消息不自动撤回。现有 `/cancel` 仍只取消尚未提交的排队输入。

不能保证所有回复都能完整送达；长文本可能截断，网络异常可能只送出前几条。网页状态会说明这种可能，不把它写成“全文已送达”。

## 5. 建议这次批准的范围

**采用上述本地规则：最多3条、最小1秒间隔，新回复默认启用；保留切回按长度分条的开关。** 网页先使用准确但保守的状态说明，不新增“已发送1/3”等精确统计接口。

获批后只做真实环境人工验收，重点看：短回复是否完整、多段回复是否自然、特殊文本是否被拆坏，以及连续追问、部分失败和重启后是否重复发送。详细依据、接口定位、异常矩阵、迁移与验收剧本保留在[技术参考](QQ自然分条回复-技术参考.md)，审核主方向时无需逐项阅读。
