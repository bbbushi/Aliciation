# 04 上下文观测与可解释性

> 这条线解决「一条回复为什么这样说」：把装配与调用做成可观测、可解释、可追溯，并让压缩与整理也有完整证据链。

**文档**：`docs/设计文档/上下文组装优化/上下文观测*、source_continuation*、多批compact*、审查开销*、对话压缩*、互动习惯*`

---

## 1. 一条回复可查清装配（观测插件）

**设计方法**：

- **核心轻量采集 + 核心保管记录 + 可选观测插件**；三栏页（请求列表 → 调用过程 → 最终输入）按用户参考的 dsh-context 原生复刻。
- 插件只走公开 HTTP 投影，**不直读 SQL 或用户目录**；核心不 import 插件 Python。
- P0 正文读取加核心归属校验（body 必须携带 request_id，裸 hash 分立拒绝）。

**用户裁定**：展示形态按用户参考复刻；插件开关与元数据/正文采集三态分立控制。

**源文档**：上下文观测插件-架构与施工设计-v1-20261107

## 2. 观测做成通用 SDK

**设计方法**：

- 纯标准库四模块：contract / freeze / observer / sink，采集、存储、查询、展示解耦。
- **两种接入必须同时存在**：组装接入记录来源/选择/排除原因；调用接入在模型客户端边界冻结最终参数——「本次快照 = 本次请求」。
- 尝试三态区分：进入调用 / 响应开始 / 完整结束；证据缺口如实记录，**不为补证据重发请求**。

**用户裁定**：交付形态定为 SDK 核心采集 + 核心保管 + 固定官方 addon 查看。

**源文档**：上下文观测SDK-补充设计-v1-20261107

## 3. 完整上下文窗口 + 滚动留存

**问题**：旧策略累计十请求后永久停止，后续请求无正文可查。

**设计方法**：

- 请求与调用旁「查看完整上下文」：按真实 messages 顺序显示角色/正文/工具调用，可看 SDK 工具定义与记录到的模型参数。
- 改为**滚动留存**：每个新请求均采集，原子保存最近 10 个采集请求；7 天 / 50MiB / 单条 200000 字符仍生效，滚出即不可读。
- 共用正文按**引用计数回收**，不随旧请求退出误删；清单损坏则停止正文读写、不猜授权；不为 body=none 历史补画正文。

**用户裁定**：直接要求添加；首次部署失败如实记录未冒充成功。

**源文档**：完整上下文窗口-设计与实施-20261111、滚动正文留存设计-v2-20261111、设置开关-设计与实施-20261117

## 4. 目录投影瘦身（source_continuation）

**问题**：来源接续出处目录 7029 字符、占首轮请求正文 38%。

**设计方法**：

- **先复核再定目标**：用真实快照纠正估算——按相同来源集合分组、策略取「公共基底 + 每包差异」（五份贴吧 policy 实际各不相同，不能整份归并）；7029 → 3213 字符（约 −54%）。
- 目录格式 v2：每来源一条真实 packet_id；S 编号仅本块展示不作工具引用；预算预留与最终发送共用同一渲染函数。
- 去重只改展示，不解除来源依赖。

> **用户裁定**：认可方向并要求施工；**明确不预先承诺 1500 字符或同比例费用下降**。

## 5. compact 证据链

**问题**：连续多批 compact 时旧批事项证据无法重建，审核失去依据。

**设计方法**：

- 用已有批次账本追溯：按同 epoch/渠道合并各批 processed_pairs，逐对重新核准资格、角色与冻结版本。
- 摘要本身不当作事实依据；证据不可重建则在模型调用前失败（prior_evidence_unavailable）。
- 预算不足**明确失败不静默截断**；提交前再核活动状态，变化则以 stale_input 结束不发布。

**用户裁定**：不改数据库格式、不复制原文、不要求用户重置。

**源文档**：多批compact证据链修复-实施与人工验收-20261109

## 6. 前情退休与审查开销

**设计方法**：

- recap_dispositions 关系表（retire / supersede / end_topic），单向生命周期，**只有用户确认的操作生效**；模型只能返回有界提议，不能调用管理 API。
- 调用依赖图与可归因观测字段（request/call/attempt/parent、purpose、实际发送模型指纹、usage_status）；失败跨度靠显式单次授权重试。

**源文档**：审查开销与前情退休-契约草案-20261104

## 7. 压缩与整理双维护

**设计方法**：

- compact / tidy 两条独立流程：compact 产出接续状态 + 合格候选 + 证据引用 + 压缩边界。
- 「清除」首先定义为**移出默认活跃上下文**，原文按原资格可追溯。
- tidy 决策顺序：先执行失效/撤回/硬期限 → 保留用户保护与未结事项 → 按时间与真实使用排序 → 合并/浓缩 → 不确定时保留差异。
- 轮末只做廉价阈值检查排队；**聊天优先于可延迟维护**；模型不拥有维护工具；自动触发默认全关。

**源文档**：对话压缩与记忆库整理-双维护流程设计草案-v1-20261109

## 8. 互动习惯指引

**问题**：24 轮复盘发现——主动接话弱、反问收尾、收到反馈行为不变、过度解释用户动机。

**设计方法**：

- 新增纯标准库、无 I/O 的 interaction_policy：一份**有版本**的互动指引（451 字符）在稳定系统前缀注入一次。
- 原则：先回应本轮内容；有具体作用才问；用户要求起头时先给内容；收到明确反馈**直接改变下一条行为**；不把反问/不知道解读为回避。
- 不设问句配额、不按标点删句、不加付费调用或行为分类器。

**用户裁定**：范围由用户限定为该四项复盘问题；不重写用户私人表达包。

**源文档**：互动习惯优化-设计与实施-v1-20261109
