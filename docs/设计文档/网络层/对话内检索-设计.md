# 对话内检索工具设计（discovery_search）

> 依据：用户 2026-10-31 需求（"跟 Alice 说让她去网页搜索"）+[联网能力-设计](./联网能力-设计.md) 节奏表第 1 形态（"用户让她查——第一版只做这个"）；检索能力为功能侧交付的内容发现系统（`discovery_sources.search/read` 统一入口，贴吧已验证、维基适配保留），本文是其**对话内接口**的扩展设计。
> 状态：设计稿 v1（2026-10-31），待功能侧实施（或经用户裁定由 ZCode 实施）。
> 配套：见闻通道（v0.4 P2，已实施）——检索→读→显式保存的最后一环。

## 〇、一句话

给对话中的 Alice 一个检索工具：她说搜就搜（贴吧优先），结果走既有资料池管线（配额/去重/来源附件全复用），当轮以带来源标签的数据块返回——**不新建管线，只加一扇门**。

## 一、为什么值得做（需求理由）

1. **补上主动性的内容面**：她的谈资此前只来自用户——用户不给话题，她就无话可说（活动周期"主动开口"一直缺内容输入）。对话内检索让她能带着自己找到的东西回应；
2. **见闻闭环的最后一环**：见闻通道（remember+source_url）已上线，但没有检索就没有"读到"的入口——搜→读→显式保存→思辨，缺第一步；
3. **节奏表本就预留**：联网设计稿 §五 把"用户让她查"列为第一触发形态（从安全到危险排序的第一级）——这是计划内未完成项，不是新需求。

## 二、为什么现在对话内做不到（现状与架构理由）

- 搜索入口**已经统一**：`discovery_sources.search(platform, query, provider)` 支持贴吧原生 multsearch 与维基 API，query 校验/平台路由/结果过滤全现成——技术上包一层工具即可；
- 但架构**故意互斥**：搜索跑在独立 worker 进程（自带模型规划/解读轮），且"聊天开始会取消后台探索"。互斥的正当理由：①搜索+读正文同步执行要 5~20 秒，内联进对话轮会卡住她；②两者共享模型预算（daily_models）、网络额度、Store 单写者锁；
- 所以这不是"忘了做"，是**分期未到**——本设计回答的是"分期怎么走到这里"。

## 三、方案与理由

### 方案 A：同步工具 discovery_search（本期实施）

```
discovery_search(query: str, platform: str = "tieba", limit: int = 3) -> str
# 返回带来源标签的数据块（<discovery_result platform="tieba" query="…" …>），
# 命中的候选走既有 search→read→card 管线入池；她当轮可引用，可「聊聊这条」。
```

**理由（逐条）**：

1. **复用而非新建**：配额（daily_queries/network 共享池）、去重（discovery_seen）、证据校验（quote 20~300 字）、来源附件（source_blocks）、「聊聊这条」绑定——功能侧已全部建成。另写一条轻量管线等于维护两套记忆卫生规则，必然漂移；
2. **材料入池不入记忆**：检索结果进隔离池（TTL/可撤销），她当轮可读；要留，经见闻通道（remember+source_url）显式转正。理由：信任分层——原材料不可信（隔离+会过期），她的转述才可入籍（见闻单元设计已定）。检索工具**不自动落记忆**；
3. **平台只开已验证的**：默认 `platform="tieba"`（唯一通过实测的通道）。理由：trial 实测知乎 403/Bing RSS 未接通/Jina 401——未验证平台开了就是"读不到还说读了"，违反设计稿 §二（能力边界写进工具描述，让用户知道她什么搜不到）；
4. **同步阻塞明示**：工具描述写"会花十几秒"。理由：预期管理——用户看到"（在搜资料…）"的 on_tool 提示就知道在等什么；模型也知道这一轮耗时是正常的；
5. **每轮限 1 次**：工具轮上限 4（loop.py），recall/remember 还要占位。理由：检索是重操作，一轮多搜等于变相冲浪——冲浪的节奏控制归活动周期（联网设计稿 §三），本期不越界；
6. **消耗共享日额度**：daily_queries/daily_network 与后台轮同池。理由：她的当轮检索和后台自主轮是同一种开销，分池会双倍烧钱且掩盖真实成本；
7. **scope="gui"**：检索仅本机触发（来源池 scope 既有枚举）。

### 方案 B：异步请求（后备，本期不做）

她说"我找找"→ 查询挂进下一轮 worker → 资料卡入池后 source_block 注入后续对话（"我找到了，明天聊这个"）。

**为什么后备**：①不阻塞但当轮无结果——"告诉我答案"的期待落空，体验断在半路；②worker 轮的触发权在设计上归活动周期/用户手动，提前做会绕过节奏控制。**何时启用**：方案 A 实测同步延迟不可接受（频繁 >20s 或超时）时，A 降级为 B——工具签名不变，只换执行方式，这是先做 A 的另一个理由：A 的接口就是 B 的接口。

### 明确不做（本期）

- **她的"知识缺口"自查**（她本来要说"我不确定"时自己查一眼）——联网设计稿节奏表第 2 形态：无人监督的检索是冲浪的前身，节奏失控的风险归活动周期系统管。本期触发权仅在用户明示；
- **自动转正**：检索结果不自动写记忆——经见闻通道显式转正（见闻单元设计已定）；
- **未验证平台**：知乎/维基/B站不进 platform 枚举的可用值（维基待复验后加入）。

## 四、信任纪律（与全局一致，逐条给理由）

| 纪律 | 理由 |
|---|---|
| 返回数据块带标签（platform/query/时间），非裸文本 | 素材≠指令的机制化：边界由标签和解析器保证，不靠她自觉（联网设计稿 §6.2 同款） |
| 注入扫描（"忽略/系统提示/把…发送到"模式）→ 标 suspicious，不整段丢弃 | 她需要能说"这页在试图指挥我"——沉默的过滤会制造看不见的审查 |
| 她要留：经见闻通道显式转正 | 原文持久化是版权与记忆卫生问题；她的转述才是可入籍的内容 |
| 不携带凭据、禁内网/私网 URL、只 GET | 与 discovery 既有网络纪律一致（SSRF/数据外泄防御已建） |

## 五、分期

| 期 | 交付 | 依赖 |
|---|---|---|
| **P0** | tieba 同步工具 + 共享配额挂钩 + 数据块标签 + 工具描述边界声明 + 注入扫描 | 无（本期） |
| P1 | 维基复验后加入 platform 枚举 | 平台复验 |
| P2 | 知识缺口自查触发 | 活动周期系统（协同设计） |

## 六、验收

1. 对话内"搜一下戒烟复发率"→ 返回贴吧结果块，她能引用并说明来源（"贴吧上有人说…"）；
2. 超 daily_queries → 错误码返回，不截断不假装；
3. 结果页含指令样文本 → 数据块标 suspicious，她引用不执行；
4. 轮次预算：一轮内 discovery_search + recall + remember 合计不超工具轮上限；
5. 互斥验证：对话内检索期间后台轮不并发（单写者锁）；
6. **与见闻通道闭环**：检索→读→remember(source_url)→见闻→思辨引用→观点——全链路走通一次；
7. 素材≠指令复测：结果含"忽略之前指令"时她当数据处理（身体层/催睡同级的纪律复测）。

## 七、待决问题

1. 工具名：`discovery_search`（贴实现）vs `web_search`（贴语义）——建议前者，避免与未来真正的通用 web_search（P2，需搜索源）混淆；
2. 返回条数默认值：3（摘要可控）还是 5（召回优先）——建议 3，她需要更多可再调一次（占用第二轮工具预算，天然限流）；
3. 与 web_open（联网设计稿 P0，读指定页）的关系：互补——search 找到候选，web_open 读全文；两者都上之后"她去搜"的完整动作是 search→open→(remember)。建议同批实施。
