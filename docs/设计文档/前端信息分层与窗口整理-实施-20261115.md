# 简洁主题与前端信息分层

## 呈现原则

**中心原则（用户最终补充，2026-11-15，仅记录）：让用户每一步接受的信息量刚刚好，以减少认知负担为目标。** 简洁的中心不在于减少信息量：信息太少会显得空，也可能不足以理解和行动；信息太密集则让人疲劳。设计需要在当前步骤提供足够且适量的信息。

此前的克制呈现、分步骤决策、按需展开与直觉反馈，都应服务于这个中心原则。不能单凭文字更少、按钮更少、留白更多或详情藏得更深，就判断设计更简洁。本次仅记录该原则，不修改代码。

新增独立主题 minimal，入口为“设置 → 外观 → 界面主题 → 简洁 · 专注对话”。不自动切换用户当前主题，也不改变原有默认值。仅在新主题下减少装饰，将详细配置、历史和技术记录通过按钮打开窗口；room/legacy/endfield 保持原有布局。

## 用户补充：克制呈现与逐步展开（2026-11-15，仅记录）

本节记录用户对“简洁”的进一步说明；本次不修改代码。前述减少装饰与窗口整理属于已施工的第一步，不代表已经完整实现本节意图。**下述 Codex 界面例子仅用于解释何为简洁，不作为具体施工依据。**

- **简洁关注每个页面的信息呈现是否克制。** 不以控件、文字或功能的数量越少越好作为目标。
- **信息表达应当清晰、易辨认、凝练。** 具体采用文字、图形或其他形式，应结合 Alice 相应页面的需求确定。
- **少量解释在需要时出现。** 初始页面呈现必要信息，进一步解释随用户的了解需求提供。
- **更多信息随着用户的需求逐步展开。** 用户主动需要了解或修改时，再提供详细内容和相应页面/窗口，不把说明、细节和高级参数一次铺满。
- **这个原则适用于每个页面。** 不仅是聊天主界面，也包括设置、思想与探索、内容发现及详情窗口；把全部文字搬进弹窗后仍一次堆满，也没有达到这一目标。

### 决策组织原则：秩序、条理和简单（用户补充，仅记录）

面对需要用户决策的操作，每一步呈现的选择应尽可能少，避免让用户在短时间内连续权衡大量选项。复杂操作按合理顺序分步骤进行，在对应步骤呈现当下需要决定的内容。

用户总结的核心是：**秩序、条理和简单。** 这里关注的是降低同一时刻的决策负担、让流程容易理解，不据此直接删减必要功能，也不机械地把每个选项都拆成独立步骤。具体分组与步骤划分留待后续设计；本轮不施工。

### 反馈设计原则：让操作及结果可直觉感知（用户补充，仅记录）

在保持简洁、克制呈现的同时，反馈应帮助用户直接理解自己的操作及其结果，减少阅读长说明、猜测状态或额外推理的负担。用户希望通过图形、颜色等抽象反馈，就能直觉地理解发生了什么。

反馈覆盖以下内容：

- **操作前**：当前是否可以操作，操作能否触发，以及可能产生什么结果。
- **操作时**：操作是否已经被触发或接收，当前是否正在处理。
- **操作后**：实际产生了什么结果，当前处于什么状态。

反馈本身也应简洁、有条理，与当前操作相关；更具体的解释在用户需要时进一步呈现。预期或可能的结果与实际已发生的结果应能区分，避免用户把点击、处理中和完成混为一谈。

本节记录的是反馈目标，不固定图标、颜色含义、动画或控件方案；具体表达另行设计。本轮不修改代码。

### 概念说明示例：Codex（不作为施工依据）

用户举例：Codex 界面通过图形凝练信息、提高辨识度，鼠标悬停时才提供少量解释，用户需要时再呈现更多内容。此处用于说明“克制呈现、按需展开”的含义，不要求 Alice 复刻 Codex 的布局，也不据此要求大量使用图形或固定采用悬停交互。

后续评估应关注用户能否快速辨认功能与状态，以及需要时能否自然获得更多信息。具体布局、图形、说明方式及交互需要另行设计；该例子不直接生成施工任务或验收条目。
