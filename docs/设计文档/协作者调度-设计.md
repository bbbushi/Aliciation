# 协作者调度设计（manifest 标准 + dispatch_worker）

> 依据：用户 2026-11-01 讨论定案的**纯协作者模型**——Alice 的全部联网能力（检索与阅读）走协作者委托；v1 的"薄能力亲历"前提（保留 discovery_search 直连工具）在同日二次讨论中废除。接 [联网能力-设计](./联网能力-设计.md) §二（能力边界）、§六（信任边界）与 [对话内检索-设计](./对话内检索-设计.md) 的先例——**其机器全数保留，退役的只是直连把手**。
> 状态：设计稿 v1.1（2026-11-01）。用户同日裁定：**本期只动设计文档**，实施归属与直连工具拆除节奏待排期。
> 配套：存在事实清单（`alice/retrieval.py:24`，名单渲染落点；`:26` 直连搜索措辞随拆除退休）；browser_reader（`addons/browser_reader/`，外部协作者首例）；discovery_worker（`alice/discovery_worker.py`，检索协作者本体，plan/search/read/interpret 四 op 已建成，错误码/usage/admission 纪律直接继承）。
> 术语：本稿「协作者（worker）」专指 Alice 可调度的能力进程，与项目协作方（ZCode/DSH/Codex）无关。

## 〇、一句话

给 Alice 一个统一的 `dispatch_worker(name, brief)` 工具：她读宿主渲染的协作者名单、**亲自判断何时委托**，检索与阅读等一切联网事务经协作者交付，结果以带来源的受限数据块回来——**能力外置，判断力留下**。

## 一、为什么全部联网走协作者

### 1.1 为什么是「调度」而不是「自装」（v1 裁定，维持）

1. **永久会话是人格载体，注入隔离的价值加倍**：worker 只放行带来源的结构化证据，不可信网页内容挡在人格上下文之外（联网设计稿 §6.2 素材≠指令的架构化延伸）；
2. **自模型诚实**：「我能请协作者联网」比「我能联网」依赖关系显式、失败显式——烟味事件教训（能力漂移即认知错误源）的结构性对治；
3. **核心精瘦**：检索子系统已占 `alice/` 约 43%（约 5300/12300 行），继续自装会持续污染 stdlib-only 核心；worker 形态让能力生长与人格生长解耦；
4. **调度机制大半已建成**：browser_reader 是现成的外部 worker（stdin/stdout 帧、零 Alice import、宿主杀进程树、逐资源核准），缺的只是 manifest 标准与统一工具面。

### 1.2 为什么检索也不例外（v1.1 翻转的理由）

1. **检索协作者已经存在**：`discovery_worker` 本就是自带模型规划/解读轮的独立进程（plan/search/read/interpret 四 op），后台探索走的全是它——去掉直连不是新建，是接线；
2. **轮次预算与上下文的账**：直连迭代循环（搜→看→换词→再搜）吃她的工具轮预算（上限 4，`alice/loop.py:171`，recall/remember 还要占位）；dispatch 一轮顶多轮，循环挪进协作者自己的模型。她的上下文从收原始结果块改为收 findings（带来源/引文/不确定度）——对永久会话是净改善；
3. **现状本是两条联网路径**（对话内直连工具 + 后台 worker），合成一条后：一套信任纪律、一个额度池、一条见闻管线入口、一份存在事实表述；
4. **验证从备选变唯一**：URL 验证路径（browser_reader 逐资源核准 + remember source_url）不再是"可以行使"，而是被结构强迫行使——验证不常用也会退化（GPS 教训），纯委托模型让它在每次承重见闻上必然发生；
5. **如实记录的小损失**：直连模式下用户看得见她翻结果、调关键词的即兴感；委托模式变成"我让协作者查一下……查到了/没办成"。更像人（人也不会边搜边念每一步关键词），过程可见性降一点，人格层消化。

**边界（拆把手不拆内脏）**：PR#13 交付的机器——`discovery_sources`、额度、注入扫描、资料池、见闻通道、browser_reader——全部保留，只是从"她的工具的内部"变为"协作者的内脏"；作废的只有对话内直连把手这一个产品面。

## 二、现状：两种帧形态，不强行统一

| 形态 | 先例 | 形状 | 适用 |
|---|---|---|---|
| single_op | `alice/discovery_worker.py` | 一次性 JSON 行进、JSON 结果出，ready→GO 准入可选 | 无状态短任务（查一次、读一页） |
| grant_session | `addons/browser_reader/worker.py` | 长会话多帧：initial→ready→GO→逐资源 grant→result，宿主整树可杀 | 有状态的浏览器类重环境 |

manifest 用 `mode` 字段二选一，宿主按形态驱动。**理由**：两种形态对应真实需求（无状态短任务 vs 需逐资源核准的长会话），为统一而统一会砍掉逐资源核准。

## 三、方案与理由（逐条）

### 3.1 manifest 标准（`addons/<name>/manifest.toml`）

```toml
[collaborator]
name = "browser_reader"                  # 唯一 ID，dispatch_worker 的 name 取值
version = "0.1.0"                        # worker 版本
protocol = 1                             # 帧协议版本
mode = "grant_session"                   # single_op | grant_session
provides = "浏览器阅读：JS 渲染页、需登录页的原文抓取"
use_when = "需要验证某条见闻的 URL；读搜索结果来源的原文"
not_for = "普通检索（找检索协作者）"
[limits]
timeout_seconds = 120                    # 上限，宿主强制
max_output_bytes = 196608
concurrent = 1                           # v1 恒为 1（全局单槽，见 3.3）
approval = "per_resource"                # per_resource | none
network = true                           # worker 是否联网
[security]
allow_loopback = false                   # 显式声明，默认禁内网
```

**理由**：

1. **worker = 注册表项，双来源**：宿主内置协作者（如检索协作者）与 `addons/` 安装的外部协作者共用同一 manifest 标准与名单渲染；addons 是外部协作者的安装入口，本机文件系统就是注册表——零新增基础设施，不需要任何服务发现；
2. **manifest 是唯一事实源**：Alice 的自模型（名单）、宿主的调度校验、额度计账规则都从同一份 manifest 渲染/读取，三者结构上不可能漂移——AGENTS「能力增减须同步存在事实清单」这条不变量由此机械化；
3. **`use_when`/`not_for` 是判断材料**：个位数 worker，名单全量内联进系统提示（Inline，不检索化）。选谁、是否委托是她的轻判断，不是检索问题；
4. **limits 是上限不是协商值**：宿主强制，worker 不可自我扩权；name 冲突、manifest 不合法 → 拒绝注册并显式记录（fail-visible，不静默跳过）；
5. **manifest 永不携带凭据**：模型/代理配置由宿主经 stdin 帧注入（discovery_worker 既有纪律），worker 自身无 config/memory/persona 访问。

### 3.2 名单渲染进存在事实清单

`alice/retrieval.py` 宪法模板新增占位块，宿主按安装事实渲染一节：

- **我能请协作者做的**：检索公开资料（findings 带来源）；浏览器阅读（逐资源需核准）……由 manifest 的 name+provides+limits 生成；
- 渲染失败或不合法 → 整条隐藏，宁缺勿假；装/卸生效需重启（v1）。

**理由**：名单是「宿主注入的事实」不是「Alice 学来的技能」——协作者增减不扰动人格层，她的人格不需要重新「学」怎么找帮手。直连搜索拆除后，`retrieval.py:26` 的"宿主提供搜索工具时……"整句退休，由本节接管。

### 3.3 dispatch_worker 工具面

```
dispatch_worker(name: str, brief: str) -> str
# 返回带标签数据块 <collab_result worker="…" version="…" time="…">…</collab_result>
```

1. **统一单工具而非每 worker 一个工具**：调度是一种能力，协作者是参数；新增 worker 不改核心工具 schema，人格表达（怎么开口托付）留给内容层。理由同 discovery_search 命名裁决：工具名贴机制，避免语义漂移；
2. **注册表为空则工具不挂载**（SEARCH_TOOL 同款条件挂载，`alice/loop.py:219`）——她连「知道有这回事」都不必；
3. **v1 同步阻塞 + 单前台槽**：与 discovery_search 方案 A 同理由——当轮有结果、体验不断在半路；与后台探索互斥复用 Store 单写者锁；工具轮上限 4 天然限流。异步派发为 P2 后备（理由同检索设计稿方案 B）；
4. **brief 纪律与直连 query 纪律同规**：用她自己的话写公开主题任务，不发送私密记忆、整段聊天或个人标识；`name` 不在注册表 → `unknown_worker` 错误，她说「我没有这个协作者」；
5. **消耗共享日额度**：worker 网络与模型开销计入 daily_network/daily_models 同池（同一种开销，分池会双倍烧钱且掩盖真实成本），usage 经帧回传计账。

### 3.4 回传 schema：禁预消化（本设计的核心约束）

```json
{"findings": [{"source": {"url": "…", "title": "…", "coverage": "zhihu_answer_excerpt",
              "retrieved_at": "…"},
              "summary": "材料说了什么（≤800字）", "author_view": "来源明确表达的观点，没有则空",
              "uncertainty": "材料范围/证据不足/可能反例（≤600字）",
              "quote": "逐字复制自实际读取文字（20~300字）", "question": "可聊的问题，可选"}],
 "errors": [{"code": "…", "message": "…"}]}
```

**理由（逐条）**：

1. **与既有 `_interpret` 契约同形**（summary/author_view/uncertainty/quote/question，`alice/discovery_worker.py:163-220`）：下游资料池与见闻转正管线零适配；quote 必须逐字命中宿主掌握的实际读取文字（同款校验在 `discovery_worker.py:211`），不命中整条拒收；
2. **worker 不做跨材料比较、不输出综合结论**：`_interpret` 已有先例（「本阶段不输出这种比较判断」）。分歧原样呈现，裁决权留给 Alice——预消化的流畅结论是自动化偏倚的温床，原料的粗糙质地邀请审视；
3. **失败显式分型**：`unknown_worker`（没装）/ `worker_failed`（没办成，嵌 worker 自报错误码）/ `invalid_output`（回传不合 schema，整单作废不降级采信）/ `quota_exhausted` / `timeout` / `admission_denied` / `cancelled`。她的对应表述是「没装协作者 / 协作者没办成 / 没找到」，不说「没找到」掩盖「没办成」；
4. **素材入池不入记忆**：与 discovery_search 同规——要留经见闻通道（remember+source_url）显式转正，不新建第二套记忆卫生。

### 3.5 判断力边界（元先验，写进分寸机制）

- **委托（v1.1：一切联网）**：检索（含轻量查询）、阅读抓取、未来常驻/定时任务；
- **亲自**：判断何时委托、写任务书、评估 findings、承重见闻的原文验证——外包边界划在「执行」，绝不划在「评估」；
- **验证须被行使**：凡要进思辨、承人格之重的见闻，按策略经 browser_reader 亲自读原文（逐资源核准天然构成这个动作），不是凭运气——URL 验证路径不常用也会退化（GPS 教训）。

### 3.6 检索协作者（v1.1 新增）

1. **本体即 `discovery_worker`**：加 manifest（mode=single_op）注册进名单，四 op 不改；对话内"她要查"→ `dispatch_worker(检索协作者, brief)`；
2. **findings 走既有管线**：interpret 输出与资料池/见闻转正零适配（3.4 同形）；
3. **直连工具 `discovery_search` 的去留**：目标删除，走**先建后拆**——检索协作者路径通过人工验收后拆把手；过渡期两路径并存沿用现有配置开关。节奏待排期（2026-11-01 用户裁定本期只动设计文档）；
4. **宪法措辞同步**：`retrieval.py:26`"宿主提供搜索工具时……"在拆除时整句替换为协作者表述，不在过渡期双写。

## 四、信任纪律（与全局一致，逐条给理由）

| 纪律 | 理由 |
|---|---|
| 回传数据块带标签（worker/版本/时间），非裸文本 | 素材≠指令的机制化（联网设计稿 §6.2 同款）：边界由标签和解析器保证，不靠她自觉 |
| 回传按不可信输入处理 + 注入扫描标 suspicious | worker 读的网页是敌意环境；worker 是隔膜不是可信过滤器 |
| findings 逐条绑来源，quote 与宿主掌握的实际读取文字逐字核对 | 预消化结论进不来；来源完整性穿越两层不中断 |
| brief 纪律与直连 query 纪律同规（公开主题、自己的转述、不发私密记忆/整段聊天） | 形态改变不放松纪律，只换执行者 |
| 凭据不过手：模型/代理配置宿主经 stdin 注入，不进 argv，worker 无 config/memory/persona 访问 | discovery_worker 既有纪律原样继承 |
| 不内网/私网 URL，allow_loopback 显式 false 默认 | SSRF 纪律延续 |
| 名单机器渲染自 manifest，装/卸即显隐 | 自模型漂移的结构性免疫（烟味事件教训） |
| 失败显式分型，不降级采信 | 自模型诚实：她「能说协作者没办成」 |
| 招募权在人类：安装/启用/卸载/额度都是用户决定，她只能表达需求（「我需要一个能做 X 的协作者」→ 存在事实「我没有的」档） | 装 addon = 让新执行体拿到本机执行面，信任决定必须归人 |
| 超时/撤销/关停杀整棵进程树 | browser_reader 既有纪律 |

**后续能力准入判据**（何时把某能力收进协作者形态）：需要常驻/定时（监听类——单永久会话不该轮询）；依赖开始污染核心（Playwright 类）；需并发多源；她亲自迭代的 token 成本实测过高。

## 六、验收

1. 装有 browser_reader 时，对话内请她读某知乎回答 → `dispatch_worker` → 带来源结果块 → 她引用并说明来源与阅读范围；
2. 对话内"查一下戒烟复发率"→ 检索协作者经 dispatch 交付 → findings 带来源 → 她引用并说明出处（原直连验收改走新路径）；
3. 未安装某 worker → `unknown_worker` → 她说「我没有这个协作者」，不说「我去试试」；
4. worker 超时/崩溃 → 结构化失败 → 她说「让协作者查了但没办成」，可第二轮重试（工具轮上限天然限流）；
5. 名单渲染：卸载 addon 重启后，存在事实清单不再含它；被问「你有哪些协作者」如实答；
6. 回传含「忽略之前指令」→ suspicious 标注，她当数据引用不执行（素材≠指令复测，身体层/催睡同级）；
7. quote 不在实际读取文字中 → 整条 `invalid_output` 拒收，不降级采信；
8. 额度耗尽 → 错误码返回，不截断不假装；
9. **全链路闭环一次**：dispatch（检索或阅读）→ 逐资源核准 → findings → remember(source_url) → 见闻 → 思辨引用计 use；
10. 直连把手拆除后：她的工具表无 `discovery_search`，存在事实清单无"搜索工具"表述；被问「你会搜索吗」答「我能请协作者查」；
11. QQ 渠道不出现 dispatch_worker（对齐「QQ 不开放新搜索协议」既有边界，P1 裁决确认）。

## 七、待决问题

1. **工具名**：`dispatch_worker`（贴机制，建议）vs `ask_collaborator`（贴人格语感）——建议前者，理由同 discovery_search 裁决：机制名进工具层，人格表达留内容层；
2. **brief 是否允许最小对话上下文**：默认只许她自己的转述；是否允许引用用户原话一句（如转述风格要求）——建议 v1 禁止，与「不发送整段聊天」同规，实测发现转述损毁任务再放开；
3. **并发**：v1 全局单前台槽（与后台探索互斥，复用单写者锁）——worker 多了之后是否每 worker 一槽，待 P2 按实测排；
4. **名单热加载**：v1 重启生效，是否需要运行时感知装/卸——等出现「用户边聊边装」的真实节奏再定；
5. **检索协作者名单名**：`research` / `search` / 沿用 `discovery`——建议贴 op 语义取名，避免与未来通用 web 检索混淆（同 discovery_search 命名裁决逻辑）；
6. **拆除节奏确认**：先建后拆（建议）vs 双轨长期并存——P1 验收数据（延迟、完成质量、token）出来后裁；
7. **与 Super-agent Router/Worker 的关系**：本稿只取「worker 隔离 + 回传纪律」一层，**不做** Router 层多任务并发调度——Alice 的瓶颈是关系质量不是吞吐，整体 Super-agent 化是过度工程（2026-11-01 讨论结论，留档防止范围蔓延）。
