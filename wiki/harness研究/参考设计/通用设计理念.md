# Harness 通用设计理念

> 什么是 harness：模型外围的工程层，把「一次推理」变成「可持续完成工作的代理」。模型是引擎，harness 是整辆车——传动、方向盘、刹车、仪表盘。同一个模型装进不同的 harness，实测能力可以差 20 个百分点（2026 年一项跨 8 个 harness 的同模型对比：46.7% ~ 66.7%），**harness 设计至少和模型同等重要**。

## 一、通用解剖：六大组成

任何 harness——编码型、陪伴型、通用助理型——都可以拆成这六块：

### 1. Agent 循环（发动机）
`模型推理 → 工具调用 → 结果回喂 → 再推理`，直到无工具调用或达到终止条件。看似 trivial，工程难点全在细节：终止条件的拿捏（pi 刻意不设 max-steps）、可中断与部分结果保留（用户改主意时不丢状态）、消息队列（生成中用户又发消息怎么办）。

### 2. 上下文工程（燃料系统）
上下文是稀缺资源，harness 的核心职责是决定**每轮把什么放进模型的视野**：
- **分区组装**：系统提示（规则/人格）→ 慢变区（记忆/项目文件）→ 快变区（近期对话）
- **稳定前缀**：把不变的内容排前面吃 prompt 缓存，成本可以差一个量级
- **渐进披露**：不把一切塞进上下文，而是给模型索引 + 按需读取的工具（grep 目录、recall 记忆、读 README——本质相同）
- **压缩**：超长历史摘要化，保留语义丢掉原文

### 3. 工具系统（手足）
工具 = 模型影响世界的 API。设计权衡：
- **工具数量 vs 行为稳定性**：pi 的论点——工具越多，模型行为越不稳定（对 Claude Code 的观察）；Claude Code 的实践——丰富工具集配权限门。两者都对，差别在目标用户
- **描述即接口**：工具描述是写给模型看的文档，描述质量直接决定调用质量
- **校验与护栏**：参数 schema 校验、危险操作拦截（SWE-agent 的 ACI 发现：接口的护栏设计本身就影响 agent 成功率）

### 4. 会话与状态（记忆载体）
- 持久化格式（pi 用干净 JSON，可 diff 可分支）
- **会话结构**：线性日志 vs 可分支树（分支允许「先去处理支线再回来」）
- 状态外置：项目文件（CLAUDE.md / PLAN.md / TODO.md）是跨会话的轻量记忆

### 5. 扩展机制（生态位）
MCP（协议标准，生态最大）/ TS 扩展（pi，agent 可自扩展）/ skills+hooks（Claude Code）/ 纯 CLI+README（渐进披露的极致）。共同趋势：**扩展即上下文管理**——如何让模型知道扩展存在、何时读取、如何调用。

### 6. 安全与评估（刹车与仪表）
- 2026 年的收敛共识：**pre-tool hook 的 allow / ask / deny 三态门**是标准安全边界；OS 级沙箱（Seatbelt/Landlock/gVisor）作为硬边界（Codex CLI、Gemini CLI 路线）
- 可观测：发给模型的一切对用户可见
- 回归评测：改 harness 必须跑基准（Terminal-Bench / SWE-bench / 自建成长实验室——本质相同）

## 二、四对设计张力（每个 harness 的立场都在这里）

| 张力 | 一极 | 另一极 | 代表分野 |
|---|---|---|---|
| **极简 vs 功能** | 4 个工具 + <1000 token 提示 | 大工具集 + plan mode + 子代理 | pi ↔ Claude Code |
| **自主 vs 控制** | YOLO 默认放行 | 每步权限确认 + 沙箱 | pi ↔ Codex CLI |
| **上下文预算 vs 信息完整** | 摘要 + 按需检索 | 大窗口全量塞入 | 所有 harness 的永恒权衡 |
| **通用 vs 领域特化** | 通用代理框架 | 编码专用 / 陪伴专用 | OpenClaw ↔ Claude Code ↔ Alice |

没有正确答案，只有立场一致性：**一个 harness 的所有选择应该在同一极上**（pi 全线极简，Claude Code 全线功能主义），混搭是最差的设计。

## 三、编码 harness 与陪伴 harness 的分野

编码 harness 的目标是**任务的正确完成**，陪伴 harness 的目标是**关系的连续与真实**。这决定了几乎每个组成部件的形态差异：

| 组成 | 编码 harness | 陪伴 harness（Alice） |
|---|---|---|
| 循环 | 任务完成即终止 | 永不终止（单一永久会话） |
| 上下文 | 代码库、任务描述 | 人格、记忆、时间感 |
| 记忆 | 会话级 + 项目文件 | 三层记忆 + 真实遗忘（核心中的核心） |
| 工具 | 大而全（文件/shell/搜索） | 小而精（recall/remember） |
| 评估 | 通过率（SWE-bench） | 成长质量四维（广度/回归/诚实/拟人） |
| 最大风险 | 破坏代码 | 编造记忆、病态依恋 |

编码 harness 的经验里，对陪伴型最有迁移价值的是：上下文工程全套（分区/缓存/渐进披露）、工具少而稳的观察、以及「评估驱动迭代」的工程纪律。没有迁移价值的是任务态假设——陪伴没有 done。

## 四、一页速览

```
┌─────────────────────────────────────────────┐
│ 渠道/入口（CLI、IDE、聊天软件）                  │
├─────────────────────────────────────────────┤
│ Agent 循环（推理⇄工具⇄回喂，可中断可排队）          │
├──────────────┬──────────────────────────────┤
│ 上下文工程     │ 工具系统（少而稳 vs 大而全）        │
│ 分区/缓存/披露  │ schema 校验 / 危险操作门          │
├──────────────┴──────────────────────────────┤
│ 会话与状态（持久化 / 分支 / 外置记忆文件）           │
├─────────────────────────────────────────────┤
│ 扩展机制（MCP / 自扩展 / skills）                │
├─────────────────────────────────────────────┤
│ 安全（allow/ask/deny 门、沙箱）与评估（基准回归）    │
└─────────────────────────────────────────────┘
```
